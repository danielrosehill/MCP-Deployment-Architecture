# v3 — 2026-07-27

Two changes versus [v2](v2-2026-04-28.md), both about how things *reach* each
other rather than what runs where: the mesh VPN is promoted from a remote-access
convenience to the **backbone**, and a **skill server** joins the aggregator as a
second, complementary answer to context load.

The component inventory from v2 is otherwise intact. Nothing was torn out.

## What changed

### Networking — the overlay mesh becomes the backbone

v1 and v2 listed two remote-access options side by side: Cloudflare Tunnels for
public reachability, Tailscale for "private mesh networking when on the move".
They were peers, and the tunnel was the one that got used.

That is inverted in v3:

> **Every machine the operator owns is on the tailnet. When one of them needs to
> reach another, that is the path — no tunnel, no service token, no port
> forward.**

The reasoning:

- **Peer identity replaces a shared secret.** Both ends are already mutually
  authenticated by WireGuard keys. Putting a bearer token in front of a host you
  already control adds a long-lived credential that has to be pasted into every
  client config and rotated by hand, and it buys nothing that the mesh did not
  already give you.
- **Per-device revocation and stable names**, from one admin console, instead of
  a secret with no expiry and no per-device story.
- **One path that works identically on-LAN and off.** This is the part that
  quietly deletes a whole problem — see below.
- **No dependency on a third party being up** for two machines sitting on the
  same LAN, and no round trip out of the house and back for local traffic.

#### The anti-hairpin workaround becomes unnecessary

v2's README carried an "anti-hairpin note": LAN clients had to be steered to the
LAN address at the DNS level so that traffic to the external hostname would not
loop out through the tunnel and back in. That was split-horizon DNS papering over
the fact that the same service had two addresses depending on where you stood.

With the mesh as the backbone, the client uses **the same overlay address from
everywhere**. There is no second address to hairpin to, so there is nothing to
work around. The DNS trick can retire with the problem it solved.

A DNS name for an owned service is now simply an unproxied A record pointing at
the overlay IP.

#### What did *not* move, and why that matters

**Public ingress stays.** This is a deliberate limit on the principle above, not
an unfinished migration, and it is worth stating plainly because "mesh is the
backbone" invites the conclusion that the tunnel should be torn down.

A third-party MCP client — a hosted-agent connector, anything in a browser
sandbox — **cannot join the mesh**. Worse, and this is the binding constraint:
such a client typically **cannot send custom authentication headers either**. The
connector UI gives you a URL field and expects the endpoint to authenticate the
caller itself, through a flow it can drive. There is nowhere to paste a header,
and no mesh to join from inside someone else's cloud.

So for that class of client a mesh-only endpoint is not merely inconvenient — it
is unreachable *and* unauthenticatable. Going mesh-only would foreclose those
integrations silently, and the failure would surface much later as "the connector
doesn't work".

The consequence for how the public endpoint is secured: a service token is the
wrong instrument there, because *sending it* is precisely what the client cannot
do. Public ingress needs auth the client can complete unaided — an identity
provider login it can render, or OAuth on the MCP server itself, which is what
the MCP spec expects of a remote server.

**The shape, stated once:** mesh is the backbone and the default for everything
you own; the public tunnel is the ingress for clients that can be neither on the
mesh nor trusted to send a header.

### Tool discovery — a skill server alongside the aggregator

v1 framed tool bloat as an aggregation problem and solved it by composing narrow
tool sets upward through tiers. That still holds, and it still is not enough: an
aggregated catalog large enough to be worth having is also large enough that
loading every tool definition into every session is the dominant context cost.

The two obvious escapes both fail:

- **Load everything.** The tool definitions alone crowd out the work.
- **Configure per project which servers to attach.** Time-consuming to maintain,
  and inflexible the moment a session needs something the project's list did not
  anticipate.

v3 adds a third component: a **skill server** holding capability definitions —
skills, procedures, instructions — retrieved **on demand** rather than mounted
into context up front. The agent searches for what a task needs and pulls only
that.

The implementation in use is [**OpenViking**](https://github.com/volcengine/OpenViking)
(volcengine), a context database that treats memory, resources and skills as a
traversable filesystem addressed by `viking://` URIs, with tiered retrieval —
abstracts first, full content only when asked for.

#### How the skill server and the aggregator divide the work

They are complementary, not competing, and the split is clean:

| | **MCP aggregator** | **Skill server** |
| --- | --- | --- |
| Supplies | Tools — the ability to *act* | Procedures — the judgement about *how* |
| Answers | "What can I call?" | "How is this done here?" |
| Loading | Tool definitions, resident in context | Retrieved on demand, transient |
| Grows by | Registering an upstream | Adding a skill document |
| Cost of breadth | Paid every session, in context | Paid only when retrieved |

The aggregator gives **breadth of access** through one endpoint with namespaced
upstreams. The skill server gives **depth of know-how** without paying for it up
front. Neither substitutes for the other: a skill that says "here is how we file
an invoice" is worthless without an invoicing tool to call, and a large tool
catalog with no procedural layer forces every session to rediscover the same
sequences.

The relationship to v1's tiering: hierarchical aggregation reduced *tool count*
per client. Progressive retrieval reduces *everything else* — the instructions,
conventions and worked sequences that would otherwise have to live in a
permanently-loaded system prompt.

## Net effect

- **Mesh VPN (Tailscale)** — the backbone. Default path between all owned
  machines; services bind to the overlay interface.
- **Public tunnel + identity-provider auth (Cloudflare)** — ingress for clients
  that cannot join the mesh or send headers. Demoted in traffic share, retained
  in role.
- **MCP aggregator (MCP Jungle)** — unchanged in function; one endpoint,
  namespaced upstreams.
- **Skill server (OpenViking)** — new. Progressive, on-demand retrieval of
  skills and procedures.
- **Object storage / file staging (MinIO)** — unchanged from v2.
- **LAN device tier** (Home Assistant, OPNsense, NAS, SBCs) — unchanged.
- **Split-horizon DNS for anti-hairpin** — retired, obsoleted by the backbone.

## Open items

- Public ingress still fronts an endpoint whose auth is header-based. Until it
  offers a browser-completable login or server-side OAuth, bare-URL connectors
  cannot use it — the integration this iteration argues for is documented but not
  yet enabled.
- Retire orphaned tunnel hostnames and access policies left over from services
  that have since moved to the mesh.
- The skill server's retrieval quality is only as good as the skills written into
  it; no convention yet for what belongs in a skill versus a tool description.
