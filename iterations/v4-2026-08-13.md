# v4 — 2026-08-13

v4 extends the control surface from one primary site to a federation of independently useful site gateways. It also records the context-efficiency model that makes a very broad tool catalog workable for a single primary operator.

![Federated MCP control surface](../diagrams/v4/1-federated-sites.png)

## What changed

### A remote site is now one upstream

A U.S. site—called **Burlington, Vermont** here as a pseudonym—runs MCP Jungle on an Orange Pi. That gateway aggregates three local upstreams:

- Home Assistant, for the site's exposed physical controls;
- host control on the Orange Pi; and
- a local label printer.

The primary-site gateway registers the whole Burlington gateway as one upstream. A representative call therefore follows this route:

```text
operator
  → primary MCP gateway
  → Burlington gateway registered as one upstream
  → Home Assistant MCP server
  → selected entity or service
```

Only one gateway connection traverses the wide-area link. Fan-out stays within the remote LAN, and clients at the remote site can use their local gateway even if the WAN or primary site is unavailable. This is primarily an availability and administrative-boundary improvement; measurements show that transatlantic latency is not large enough to justify the design by itself.

### Origin remains visible in every tool name

The primary gateway already exposes its own Home Assistant, host-control and printer tools. Flattening a second site's identically named tools would make it dangerously easy to control the wrong physical location.

The upstream gateway's namespace is therefore preserved beneath the site name:

```text
burlington__home-assistant__HassTurnOff
burlington__box-control__run_command
burlington__label-printer__print_label
```

The double prefix is load-bearing provenance. Any future site should receive an equally unmistakable site identifier, and duplicate routes to the same host-root or physical-control tool should be removed.

### The deployed WAN hop is Cloudflare Access

The Orange Pi publishes its gateway on LAN, tailnet and public-tunnel endpoints. The actual primary-gateway registration currently uses the public Cloudflare endpoint with Access service-token headers.

This differs from the generic “tailnet first between owned machines” rule for a concrete operational reason: MagicDNS from inside the primary gateway container is unreliable, while pinning a tailnet IP risks a silent failure if the device rejoins with a new address. The public route's expiring credential has maintenance cost, but it fails clearly with HTTP 403.

A tailnet-only gateway-to-gateway hop remains the preferred variant where stable naming and routing work. It should be paired with ACLs or grants that authorize only the required source workload, destination gateway and port. A default-allow tailnet is a private transport, not sufficient fine-grained authorization.

## Single-user breadth and context efficiency

![Single-user namespace and discovery model](../diagrams/v4/2-context-efficiency.png)

### One broad namespace is the normal surface

The deployment mostly serves one operator. The default personal namespace therefore acts as a **super-namespace**, deliberately containing nearly the entire catalog: personal and business SaaS, infrastructure, primary-site devices and the federated Burlington site.

This avoids declaring a predicted working set for every project. Such declarations are maintenance-heavy and fail when an exploratory session needs a capability nobody anticipated at connection time. The broad namespace makes capabilities reachable; it does not require every capability's detailed schema or procedure to occupy the active prompt.

### Overlap creates another auth surface

A narrower namespace intentionally duplicates selected tools from the personal super-namespace. Its purpose is to model another principal or trust context—for example, a household surface with Home Assistant and shared utilities—behind a separate credential and policy.

This overlap is by design. Namespaces answer **who may reach what**. They are permission boundaries, not project folders and not the primary lever for context optimization. The primary operator's namespace does not need to lose tools merely because a shared namespace also exposes them.

### Progressive discovery has two cooperating parts

The context-efficiency mechanism separates tool schemas from operational know-how:

1. The **toolbox meta-MCP** exposes four bootstrap operations: list servers, list matching tools, describe only selected schemas, and invoke a named tool. A toolbox-only namespace gives clients a minimal connection surface while retaining access to the catalog through deferred calls.
2. **OpenViking** stores skills, procedures and conventions. An agent uses semantic `find`/`search`, then `read`, to load only the relevant operational context.

The primary gateway still owns tool reachability and routing. The toolbox progressively exposes actionable schemas; OpenViking progressively exposes judgement about how those tools are used. Calling both “tool discovery” obscures a useful boundary, so v4 names the two roles separately.

There remains a non-zero cost for advertising tool names in the broad namespace. That cost is accepted for the default operator surface. Clients for which even that bootstrap cost is excessive can use the toolbox-only namespace.

## Security posture

This model gives one operator a powerful global control surface. In the deployed environment, possession of a service token—or membership of a permissive tailnet on credential-free paths—may grant access to physical controls, network administration and host-root commands at more than one site.

That is a conscious personal deployment trade-off. It is not a recommendation for organizations, multiple mutually untrusted users, regulated workloads or safety-critical control. Those environments should add least-privilege per-principal namespaces, identity-aware gateway authorization, restrictive network ACLs, per-site credentials, audit trails, approval gates for consequential actions and an explicit cross-gateway policy for tools, prompts and resources.
